# Requirements: marmot-ts

**Milestone:** v2.1 Protocol hardening and group images
**Defined:** 2026-10-08
**Review status:** Requirements and roadmap approved by the user on 2026-10-08.
**Core Value:** A downstream client can join a Marmot group and exchange messages that interoperate byte-for-byte with spec-conformant peers across supported runtimes.

## v2.1 Requirements

Scope confirmed: Phase 12 protocol/client follow-ups, then Phase 13 complete group-image workflow.
Requirements below are confirmed from the selected findings and historical milestone research (retained in Git history).
All 23 requirements below were verified at milestone closeout; see [validation summary](v2.1-ROADMAP.md).

### KeyPackages

- [x] **KP-01**: Developers can create and recognize reusable KeyPackages using the adopted empty-data last_resort_key_package component 0x0004 in the KeyPackage app-data dictionary; producers stop emitting the legacy extension marker.

- [x] **KP-02**: Developers can publish, rotate and purge KeyPackages without a relays tag on kind 30443, using configured or locally retained routing information and preserving the publication slot across rotation and restart.

- [x] **KP-03**: After a successful join, consumed single-use KeyPackage init-key material is deleted; last-resort reuse remains available under the specified lifecycle, and rejected joins preserve the original private material.

- [x] **KP-04**: Developers receive a clear error for clientId or explicit slot identifiers that are not exactly 64 lowercase hex characters decoding to 32 bytes; guidance describes a stable random publication slot rather than a device label.

### Join authorization

- [x] **JOIN-01**: A join succeeds only after the MLS GroupInfo signer is identified, its account identity is validated and it is an active admin in the resulting valid group state; rejection persists no new/replacement group and consumes no KeyPackage material.

### Client behavior

- [x] **CLIENT-01**: Developers can supply proposal builders returning one or several proposals; each resolved proposal is admitted individually with matching public types on ordinary commit and founding-Add paths.

- [x] **CLIENT-02**: Live group connections serialize backfill and event batches per group through complete ingest-generator draining, preserving deduplication and trust checks and stopping intake when disconnected.

- [x] **CLIENT-03**: Applications using groups.connect() or connectAll() can observe fork-invalidated message results with enough attribution to reconcile the affected messages.

- [x] **CLIENT-04**: Applications can remove fork-invalidated rumors from supported history backends, and queries and subscribed timelines cease showing the retracted messages; custom-backend migration is documented.

- [x] **CLIENT-05**: Applications can cancel a pending idle groups.watch() promptly without waiting for another store update, with its listeners released.

- [x] **CLIENT-06**: Developers have a documented supported way to use the Marmot MLS authentication service: export marmotAuthService if it is intended public API, or record the reason and document the supported alternative after inspecting its intended use.

### Message retention

- [x] **RET-01**: Application-message kind-445 envelopes use the exact checked source-epoch NIP-40 expiry, unchanged across retries; disabled retention, undefined or unrepresentable sums, commits and proposals emit no expiry hint.

### Group images

- [x] **IMAGE-01**: Developers can encode and strictly decode canonical present and all-empty 0x8002 Blossom image states; malformed lengths, partial states, noncanonical MIME, invalid UTF-8 and trailing bytes are rejected.

- [x] **IMAGE-02**: Developers can encrypt and decrypt image bytes using fresh independent content keys/nonces, the specified image AAD and SHA-256 ciphertext binding, interoperable with the pinned spec and MDK.

- [x] **IMAGE-03**: KeyPackages advertise 0x8002 support only when the implemented codec and known-component validation are available, allowing compatible peers to negotiate group-image support.

- [x] **IMAGE-04**: Only active admins can propose, commit, clear or remove image state, with candidate-parent authorization enforced on local send, inbound admission and convergence/recovery paths.

- [x] **IMAGE-05**: Applications can read a canonical rendering-source descriptor that chooses a nonempty URL avatar before Blossom and falls back to Blossom when the URL avatar is empty or removed.

- [x] **IMAGE-06**: Applications can retrieve a Blossom image through configured endpoint/resolver and HTTP transport, verify the fetched ciphertext hash before decrypting, and obtain plaintext bytes with canonical MIME for display.

- [x] **IMAGE-07**: Admins can upload an encrypted replacement image using a fresh image-specific Nostr upload key rather than their account identity, with upload authorization and response validation for the configured Blossom service profile.

- [x] **IMAGE-08**: Admins can apply a full replacement image state through the existing MLS publish/confirm lifecycle only after the encrypted upload succeeds; a failed upload leaves canonical image metadata unchanged.

- [x] **IMAGE-09**: Admins can clear the Blossom image using the canonical empty state without implying remote blob deletion; subsequent rendering reflects the remaining URL avatar or absence of an image.

- [x] **IMAGE-10**: Missing endpoints, network failure, local resource/contact-policy refusal, hash mismatch and AEAD failure are reported as image unavailability without invalidating otherwise-valid component or group state.

- [x] **IMAGE-11**: Applications do not receive a stale image as the current canonical image after replacement, clearing or fork rewind; in-flight fetch results and caches are associated with the metadata snapshot they represent.

## Out of Scope

| Feature                                                           | Reason                                                                             |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Application UI, image editor, resizing or thumbnail pipeline      | This milestone provides library APIs, image bytes and rendering metadata           |
| Universal Blossom discovery / mandated shared server              | Endpoint/discovery profile is application configuration, not component state       |
| Remote image deletion and revocation of shared upload credentials | Clear changes canonical MLS state; v1 does not revoke disclosed server credentials |
| Durable background-upload job system                              | Not required for the confirmed library image workflow                              |
| General disappearing-message enforcement against hostile senders  | Selected follow-up is exact transport expiry signaling; it is advisory             |
| Legacy 0xf2f1 account-proof support                               | Preserve the adopted 0x8009 clean-cut profile                                      |
| Multi-device, push and QUIC data plane                            | Unselected scope                                                                   |
| Fixing every historical release finding or publishing a package   | Separately tracked release preparation                                             |
