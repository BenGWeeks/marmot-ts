<objective>
Close verification gap CR-02 (10-VERIFICATION.md truth 4 / FOUND-04: "a failed delivery is retryable per
invitee"). `NostrWelcomeDelivery.deliverMany()` currently maps every fulfilled `deliver()` promise to
`{ kind: "succeeded" }`, including a publish response in which every relay returned `ok: false`
(auth-required, rate-limited, blocked). `MarmotGroup.pendingWelcomes` then hides that invitee and
`retryWelcome()` returns the stale "succeeded" outcome without re-publishing — a member at epoch 1 who was never
told, with nothing recording it. The same misclassification flows into `GroupRuntime`'s ordinary-invite
`welcomeDelivery.outcomes`, because `deliverMany` is the one shared implementation (D-06/D-07).

Per the user's 2026-09-28 decision, this is a blocking fix: reuse the existing `hasAck()` helper (already used by
`GroupRuntime#publishToGroupRelays`) rather than duplicating it, and prove the fix at three levels — the
`deliverMany` unit, the `MarmotGroup` retry surface, and the `GroupRuntime` ordinary-invite path.

Output: an ack-aware `deliverMany`, unit + consumer tests, a runtime test double that delegates to the
production method, and one clarifying docs paragraph.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| relays → publish response | Relays report per-relay `ok` / `message`; the client must not treat an all-reject response as delivery |
| delivery report → caller | `pendingWelcomes` / `WelcomeFanoutOutcome` is the only signal an app has that an invitee was never told |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-29 | Denial of service | `deliverMany` classification (founding + ordinary invite) | high | mitigate | Apply the shared `hasAck` to every fulfilled publish; an all-`ok:false` or empty response is `failed`, so the invitee stays in `pendingWelcomes` and `retryWelcome` re-publishes. Proven at unit, MarmotGroup and GroupRuntime levels |
| T-10-30 | Repudiation | runtime test double drifting from production classification | medium | mitigate | `makeDeliverManyFromDeliver` delegates to `NostrWelcomeDelivery.prototype.deliverMany`; a negative grep pins removal of the hand-written copy |
| T-10-31 | Spoofing | a relay falsely answering `ok: true` | low | accept | A relay OK is advisory by NIP-01 semantics; this is the same trust GroupRuntime already places in relay acks for group events. Out of scope to strengthen here |
| T-10-32 | Information disclosure | relay URLs and OK messages included in the failure string | low | accept | Only relay URLs and relay-supplied OK text; no key material, Welcome bytes or recipient secrets. Stays in-process on the caller's outcome object |

No package-manager installs occur in this plan, so the supply-chain row (`T-10-SC`) is not applicable.
